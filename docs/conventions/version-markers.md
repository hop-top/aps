# Version markers

Status: active
Updated: 2026-09-03

Repo convention for docs that describe a CLI surface absent from the latest
tag. `next` integrates ahead of `main`; a page on `next` can document a command
no tagged binary has. The marker tells the reader which build they need.

## Callout

Exact form, one line, blockquote:

```markdown
> Availability: unreleased. Requires a build newer than aps/v0.6.0-alpha.0.
```

After the surface ships, the release PR rewrites it:

```markdown
> Availability: since aps/vX.Y.Z.
```

`aps/v0.6.0-alpha.0` above is the latest tag at time of writing; substitute the
current one (see [Finding the latest tag](#finding-the-latest-tag)).

## Placement

- Directly under the nearest heading that scopes the surface, before any prose.
- Heading also covers released content: add a sub-heading for the unreleased
  part first, callout under it. Never mark a released section by proximity.
- One callout per heading. No inline markers in tables, code blocks, or lists.
- Surface documented on several pages: callout on each; readers land on one.

## When to add

Same commit that documents the surface. Applies to commands, subcommands,
flags, payload fields, config keys, env vars: anything a reader would try
against a released binary and miss.

Check before writing:

```bash
tag=$(git describe --tags --abbrev=0 --match 'aps/v*')
git grep -l '<surface>' "$tag" -- docs internal   # empty output = unreleased
```

Generated pages (`docs/cli/commands.md`, cog regions) carry no callout; they
render from the tree they are built on.

## Who converts or removes

Owner: the release PR. release-please opens `chore(release): aps <version>`
against `main`; merging it creates tag `aps/v<version>`. Before that merge,
land one `docs(release)` commit ahead of it that:

1. Lists open callouts: `git grep -n '^> Availability: unreleased' -- docs`
2. Rewrites each to `> Availability: since aps/v<version>.`
3. Drops `since` callouts left from the previous release; CHANGELOG.md keeps
   the history.

Nothing else touches a callout. A feature branch never pre-fills a version;
the version is known only when the release PR exists.

## Release notes

- [CHANGELOG.md](../../CHANGELOG.md) at repo root is generated by release-please
  from Conventional Commits (`.github/release-please-config.json`). Never
  hand-edit it; the next release PR overwrites manual changes.
- Release notes live in CHANGELOG.md.
  [release-notes.md](../dev/operations/releases/release-notes.md) is historical
  (v0.2.x through v0.5.x) and stays frozen.
- `docs`-type commits are hidden from the changelog, so a callout conversion
  never surfaces there; the `since` line is the reader-facing record.
- No per-page `Last updated:` lines; they drift on every commit. Point readers
  at CHANGELOG.md instead.

Release flow: [release-process.md](../dev/operations/release-process.md).

## Finding the latest tag

```bash
git fetch --tags
git describe --tags --abbrev=0 --match 'aps/v*'
```

Tags carry the `aps/` component prefix (`include-component-in-tag` plus
`tag-separator: "/"` in the release-please config); a plain `v*` match finds
nothing.
